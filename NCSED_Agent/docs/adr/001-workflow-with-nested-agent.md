# ADR-001. Граф с фиксированными стадиями вместо сквозного ReAct-агента

- **Статус:** принято
- **Дата:** 2026-08-17

## Контекст

ТЗ описывает пользовательский путь из семи шагов и требует, чтобы на каждом
шаге пользователь получал самостоятельный артефакт, мог его принять, попросить
правку или уйти с ним. Отдельно требуется количественная оценка качества
и честное поведение в случае «данных нет».

Инференс — локальная модель Qwen3-8B на RTX 4050 (8 GB). Скорость и качество
следования инструкциям заметно ниже облачных моделей.

## Решение

Верхний уровень — `StateGraph` (LangGraph) с явными узлами по стадиям ТЗ
и типизированным состоянием, где каждый артефакт лежит в отдельном поле.
Порядок стадий детерминирован, всё содержание решает LLM.

На входе — узел-роутер с быстрыми путями (`direct_lookup`, `catalog_qa`,
`out_of_scope`) мимо полного цикла.

ReAct-цикл с инструментами используется точечно — внутри узла поиска
источников, где число итераций заранее неизвестно.

Персистентность — checkpointer на SQLite; правки реализуются через
`update_state` с перезапуском только затронутых узлов.

## Рассмотренные альтернативы

**Сквозной ReAct-агент.** Отклонён по трём причинам:

1. *Неизмеримость.* Нет выделенных стадий — нельзя померить качество
   отдельного шага и заметить деградацию после правки промпта.
2. *Артефакты появляются недетерминированно.* Требование «ценность на каждом
   шаге» выполняется только случайно.
3. *Правки ненадёжны.* Единственное состояние — история сообщений. Запрос
   «поменяй период» заставляет модель перечитать весь контекст, и нельзя
   гарантировать, что не поедет остальное.

Дополнительно: длинный tool-цикл на локальной 8B — это единицы минут на запрос
и высокий шанс развалиться в середине.

**Мультиагентная система с супервизором.** Избыточна: стадии заданы ТЗ,
делить их между агентами нечего, а стоимость координации на локальной модели
высокая.

## Последствия

Положительные:
- метрики считаются по узлам, регресс виден;
- прерывание, возобновление и правка работают детерминированно;
- граница «LLM не извлекает числа» проходит по границе узлов и проверяема;
- число вызовов LLM на запрос ограничено сверху.

Отрицательные:
- кода заметно больше, чем у `create_react_agent`;
- запросы вне предусмотренных маршрутов обрабатываются хуже, чем свободным
  агентом. Смягчается роутером и веткой `out_of_scope`;
- добавление стадии требует правки графа, а не только промпта.

## Как проверить, что решение было верным

Если по итогам eval окажется, что роутер ошибается чаще, чем в 15% случаев,
а ветка `out_of_scope` срабатывает на осмысленных запросах — значит маршрутов
не хватает, и решение стоит пересмотреть в пользу большей гибкости.
